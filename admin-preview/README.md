# Token Management Admin Dashboard — Frontend

پنل مدیریت Central Mine (خزانه، فروش محصولات، حسابداری، پشتیبانی). داده‌ها از
بک‌اند NestJS خوانده و روی آن ذخیره می‌شوند.

## فناوری‌ها
- React 19 و TypeScript
- Vite 7 برای اجرای توسعه و ساخت خروجی
- Tailwind CSS 4 برای استایل‌دهی
- خروجی بیلد یک فایل HTML واحد است (`vite-plugin-singlefile`)
- Playwright برای تست رابط کاربری

## اجرا
1. Node.js نسخه LTS را نصب کنید.
2. در ترمینال وارد پوشه پروژه شوید.
3. `npm install` را اجرا کنید.
4. `.env.example` را به `.env` کپی کنید و مقدارش را تنظیم کنید.
5. اجرای توسعه: `npm run dev`
6. ساخت نسخه انتشار: `npm run build` — خروجی در `dist/index.html`

## اتصال به بک‌اند

آدرس API از `VITE_ADMIN_API_BASE` خوانده می‌شود (`src/api.ts`):

| حالت | مقدار | توضیح |
| --- | --- | --- |
| دامنهٔ جدا / پیش‌نمایش | `https://centralmine.org/v1` | درخواست مستقیم مرورگر به API. فقط وقتی کار می‌کند که بک‌اند هدرهای CORS را برای این مبدأ بفرستد (در `main.ts` مقدار `cors.origin='*'` است). |
| دیپلوی روی همان دامنه | `/v1` | بدون CORS؛ نیاز به reverse proxy دارد که `/v1` را به بک‌اند ببرد. این حالت برای پروداکشن توصیه می‌شود. |

کلید پنل از `VITE_ADMIN_PANEL_KEY` می‌آید و به‌صورت هدر `X-Admin-Panel-Key`
فرستاده می‌شود.

> ⚠️ **هشدار امنیتی:** هر دو متغیر `VITE_*` داخل باندل JavaScript قرار می‌گیرند
> و با DevTools قابل خواندن هستند. پس `VITE_ADMIN_PANEL_KEY` یک کلید محرمانه
> **نیست** و نباید تنها لایهٔ حفاظت پنل باشد. برای حذفش از باندل، پروکسی سمت
> سرور (Caddy/nginx) باید هدر را تزریق کند — همان معماری‌ای که کامنت
> `src/guards/auth.guard.ts` در بک‌اند توصیف می‌کند. تا آن زمان پشت این پنل
> یک لایهٔ احراز هویت واقعی (Basic Auth یا ورود با JWT) بگذارید.

### دیپلوی زیر یک subpath

اگر پنل روی مسیری مثل `https://centralmine.org/admin` سرو می‌شود، باید
`VITE_BASE=/admin/` تنظیم شود تا assetها 404 نشوند. در حالت توسعه `base`
همیشه `/` است.

## رفتار اتصال و ذخیره‌سازی

`src/App.tsx` هر ۱۵ ثانیه این endpointها را می‌خواند:

```
GET /admin/state            GET /admin/sales
GET /admin/overview         GET /products?page=1&size=200
GET /admin/treasury/report
GET /admin/products/report
```

و تغییراتی را که **کاربر** انجام می‌دهد با `PUT /admin/state` ذخیره می‌کند.

دو نکتهٔ مهم که در این نسخه اصلاح شده‌اند:

1. **خطاها بی‌صدا بلعیده نمی‌شوند.** پیش‌تر هر درخواست ناموفق به `null` تبدیل
   می‌شد و پنل بدون هیچ پیامی صفر/خالی نشان می‌داد. حالا یک بنر وضعیت، علت
   شکست هر endpoint را با کد وضعیت و پیام فارسی نمایش می‌دهد.
2. **رفرش ناموفق دیگر دادهٔ سرور را پاک نمی‌کند.** پیش‌تر اگر خواندن شکست
   می‌خورد، یک DB خالی ساخته و بلافاصله با `PUT /admin/state` روی سرور
   ذخیره می‌شد — یعنی پنل دادهٔ واقعی را با مقادیر پیش‌فرض بازنویسی می‌کرد.
   حالا فقط تغییرات کاربر ذخیره می‌شوند (پرچم `dirtyRef`) و اگر هیچ endpoint-ی
   پاسخ ندهد، `db` دست‌نخورده می‌ماند.

## ساختار اصلی
- `src/main.tsx`: نقطه ورود React و بارگذاری CSS
- `src/App.tsx`: پوسته اصلی پنل، منوها، لایهٔ اتصال به سرور و اکشن‌های داده
- `src/api.ts`: کلاینت API — آدرس پایه، کلید پنل و ترجمهٔ خطاها
- `src/pages/`: داشبورد، خزانه، فروش، حسابداری و پشتیبانی
- `src/components/`: اجزای رابط کاربری مشترک و لوگو
- `src/data.ts`: مدل‌ها، انواع TypeScript، دادهٔ اولیه و توابع محاسباتی
- `src/hooks.ts`: هوک‌های رابط کاربری
- `src/index.css`: طراحی بصری، رنگ‌ها، واکنش‌گرایی و انیمیشن‌ها

## تست‌ها
```bash
npx playwright install chromium   # فقط بار اول
npx playwright test
```
`tests/fallback.spec.ts` منطق `normalizeDB` را بدون مرورگر می‌سنجد.
`tests/sales.spec.ts` و `tests/responsive.spec.ts` هنوز بر پایهٔ نسخهٔ
`localStorage` نوشته شده‌اند و با لایهٔ فعلی (که از سرور می‌خواند) هم‌راستا
نیستند — برای اجرا باید یک بک‌اند در دسترس باشد یا دادهٔ آزمایشی mock شود.
